# Extra · 事件系统架构全景：七种模式对比

> 目标：[进阶 01](https://github.com/Tur/advanced/01-%E4%BA%8B%E4%BB%B6%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1.md) 介绍了「Event 基类 + EventDispatcher」的统一管道模式（Hazel/Unity/Unreal UMG 风格）。
> 但这不是唯一解——工业界至少有 **七种** 成熟的事件系统架构，各有适用场景。
> 本文从设计哲学、类型安全、性能、解耦程度、时序控制五个维度对比它们，
> 帮你理解什么时候该用哪一种。

---

## 总览

| # | 架构 | 代表实现 | 核心思路 | 最适合 |
|---|------|---------|---------|-------|
| ① | **Event 基类 + Dispatcher** | Hazel、Unreal UMG | 统一类型继承 + 编译期派发 | 窗口/输入事件（已知事件类型） |
| ② | **Signal/Slot** | Qt、Boost.Signals2、EnTT `sigh`/`sink` | 模板化信号，不需要基类 | 一对多通知，组件间松耦合 |
| ③ | **Delegate** | Unreal Engine Delegates | 轻量函数指针包装器 | 需要反射/蓝图集成 |
| ④ | **事件队列 (Event Queue)** | GPP 经典模式、音频引擎 | Ring buffer，延迟派发 | 解耦**时序**（发送≠处理） |
| ⑤ | **发布-订阅 / 消息总线** | 自定义 EventBus | 按 topic/channel 路由 | 完全匿名发布者和订阅者 |
| ⑥ | **ECS 事件系统** | EnTT `dispatcher` | 即发 + 排队 + 组件级事件 | ECS 架构，实体间通信 |
| ⑦ | **响应式 / Observable 流** | RxCpp、ReactiveProperty | 数据流 + 链式变换 | UI 数据绑定、属性监听 |

下面逐一展开。

## ① Event 基类 + Dispatcher（你在进阶 01 已学）

```
    Event (基类)
    ├── KeyEvent
    │   ├── KeyPressedEvent
    │   └── KeyReleasedEvent
    ├── MouseEvent
    │   ├── MouseMovedEvent
    │   └── MouseButtonPressedEvent
    └── WindowEvent
        ├── WindowResizeEvent
        └── WindowCloseEvent
```

```cpp
// 派发
EventDispatcher d(e);
d.dispatch<KeyPressedEvent>([](KeyPressedEvent& ev) {
    if (ev.getKeyCode() == GLFW_KEY_ESCAPE) { /* ... */ }
    return true;
});
```

**特点：**
- 事件类型强枚举 (`EventType`)，编译期匹配
- 分类位掩码 (`EventCategory`) 支持 handler 订阅多类事件
- `handled` 字段实现传播拦截
- 适合**窗口/输入事件**——事件类型已知且有限

**局限：**
- 新增事件类型 = 新增子类 + 新增 `EventType` 枚举值
- 事件携带的数据是**强类型**的（`KeyPressedEvent` 有 `getKeyCode()`），但消息体本身不支持弱类型/动态 payload
- 不太适合「任意系统发任意消息给任意系统」的完全解耦场景

## ② Signal/Slot 模式

**哲学：** 不需要事件基类。每个信号就是一个**模板化的发布者**，槽（slot）就是任意可调用对象。

```
    Signal<void(int)> keyPressed;     // 按键信号
    Signal<void(float, float)> mouseMoved;  // 鼠标移动信号

    // 连接：完全类型安全，编译期检查
    keyPressed.connect([](int key) { /* ... */ });
    keyPressed.connect(&someObject, &SomeClass::onKey);

    // 发布
    keyPressed.publish(GLFW_KEY_ESCAPE);
```

### 代表实现对比

| 库 | 特点 | 性能 |
|----|------|------|
| **Qt Signals/Slots** | MOC 预处理器，支持跨线程队列连接 | 中等（字符串查找开销） |
| **Boost.Signals2** | 纯 ISO C++，线程安全，自动断开 (`track`) | 中等（分配开销） |
| **nano-signal-slot** | 单头文件，零分配，<1000 行 | **极高**（模板展开后几乎无开销） |
| **EnTT `sigh`/`sink`** | 基于 `delegate`，分离发布器与订阅器 | 高，适合游戏引擎 |

### EnTT 的 `sigh` + `sink` 示例

```cpp
// 信号（私有成员，只有 owner 可以 publish）
entt::sigh<void(int, int)> onResize;

// sink（公开接口，外部用它 connect/disconnect）
auto sink = entt::sink{onResize};
sink.connect<&MyClass::onResize>(myInstance);
sink.connect<&freeFunction>();

// 发布
onResize.publish(1920, 1080);
```

> 💡 `sigh` 是信号本身（内部持有），`sink` 是它的公开接口。**发布者不暴露订阅能力，订阅者不暴露发布能力**——这是 Qt Signals 做不到的。

### 与模式 ① 的对比

| | Event + Dispatcher | Signal/Slot |
|---|---|---|
| 是否需要基类 | ✅ 所有事件继承 `Event` | ❌ 不需要 |
| 新增事件 | 新子类 + 枚举值 | 新 Signal 成员变量 |
| 类型安全 | 运行时枚举 + `static_cast` | 编译期模板 |
| 订阅粒度 | 按事件类型 | 按具体信号（更细粒度） |
| 适合场景 | 统一事件管道 | 组件间点对点通知 |

**选 ② 不选 ① 的场景：** 你的系统间需要松耦合的点对点通信，而事件类型本身不需要统一集中管理。比如「渲染系统通知 UI 系统纹理加载完成」——用 Signal 比去定义一个新的 `TextureLoadedEvent` 子类更自然。

## ③ Delegate 模式 (Unreal Engine 风格)

**哲学：** 把「函数指针 + 绑定对象」打包成一个轻量对象，可广播给多个监听者。

Unreal 的分级体系：

```
Delegate (Single-cast)          Multicast Delegate
├── Static Delegate             ├── Static Multicast
├── Dynamic Delegate (反射)      ├── Dynamic Multicast (可蓝图绑定)
└── Sparse Delegate             └── Event (暴露给蓝图的事件分发器)
```

```cpp
// Unreal C++ 风格（示意，实际语法不同）
DECLARE_MULTICAST_DELEGATE_OneParam(FOnHealthChanged, float);

class ACharacter {
public:
    FOnHealthChanged OnHealthChanged;   // 事件分发器

    void TakeDamage(float amount) {
        Health -= amount;
        OnHealthChanged.Broadcast(Health);  // 向所有订阅者广播
    }
};

// 订阅
character->OnHealthChanged.AddDynamic(this, &AHUD::OnHealthUpdate);
```

**特点：**
- 不需要任何基类——`DECLARE_MULTICAST_DELEGATE` 是宏，展开成一个模板类
- Dynamic Delegate 支持蓝图/反射绑定（按函数名字符串查找）
- 和 Unreal 的 `UFUNCTION` 宏配合，引擎自动管理绑定生命周期

> 💡 模式 ③ 本质上是模式 ②（Signal/Slot）的一个特例，但它加了**反射层**和**多重变体**（Single/Multi/Dynamic/Sparse）。

## ④ 事件队列 / 延迟事件 (Event Queue)

**哲学：** 把「什么时候发送事件」和「什么时候处理事件」解耦。

```
    发送侧                    队列 (Ring Buffer)           处理侧
    ┌──────┐                ┌───┬───┬───┬───┐             ┌──────────┐
    │ 物理 │──► KeyDown ──►│   │   │   │   │──► 弹出 ──► │ 逻辑     │
    │ 引擎 │──► Collide ──►│   │   │   │   │──► 弹出 ──► │ 系统     │
    │ 音频 │──► SoundEnd──►│   │   │   │   │──► 弹出 ──► │ (每帧    │
    └──────┘                └───┴───┴───┴───┘             │  update) │
                                                        └──────────┘
```

### 为什么需要延迟？

模式 ①-③ 的派发都是**立即的**（同步）。`publish(event)` → 所有 handler 当场执行完才返回。这在很多场景下反而有害：

| 问题 | 例子 |
|------|------|
| **时序错乱** | 在物理回调里直接删除一个 entity，而物理引擎还在遍历它 |
| **逻辑在错误的时机执行** | 音频回调线程里触发 UI 更新（线程不安全） |
| **无法录制/回放** | 立即事件转瞬即逝，不能保存下来重放 |
| **优先级控制** | 立即派发按连接顺序执行，没有延迟排序的机会 |

**延迟事件把「收集」和「处理」分成两个阶段：**

```cpp
// 阶段 1：收集（任何地方、任何时间）
class EventQueue {
    static constexpr int MAX = 256;
    Event* buffer[MAX];
    int head = 0, tail = 0;

public:
    void enqueue(Event& e) { buffer[tail] = &e; tail = (tail + 1) % MAX; }

    // 阶段 2：处理（主循环的固定时机）
    void process() {
        while (head != tail) {
            buffer[head]->execute();
            head = (head + 1) % MAX;
        }
    }
};

// 游戏主循环
while (running) {
    eventQueue.process();     // ← 所有事件在这里统一处理
    updatePhysics();
    updateGameLogic();
    render();
}
```

**进阶：带时间戳的延迟**——不只是「下一帧处理」，而是「N 毫秒后处理」：

```cpp
struct TimedEvent {
    float triggerTime;
    Event* event;
};

// 可以用来实现：按键连发、技能冷却、过场动画事件编排
```

### 与模式 ① 的理想结合

```
GLFW 回调 → 构造成 Event → EventQueue::enqueue()  （收集阶段）
                                           │
主循环的固定时机 ──→ EventQueue::process() ──→ EventDispatcher::dispatch()  （处理阶段）
```

= **立即事件的类型安全 + 延迟处理的时序清洁**。

## ⑤ 发布-订阅 / 消息总线 (Pub/Sub / Event Bus)

**哲学：** 发布者和订阅者互不知道对方的存在——它们只通过 **channel/topic** 通信。

```
    发布者 A                消息总线                  订阅者 X
    ┌──────┐               ┌──────────┐               ┌──────┐
    │  系统  │──publish──►  │  Bus     │──dispatch──►  │  UI  │
    │  战斗  │   channel    │          │   channel     │      │
    └──────┘   "combat"     │ "combat" │ "combat"      └──────┘
                            │ "audio"  │
    发布者 B                │ "ui"     │               订阅者 Y
    ┌──────┐                │          │               ┌──────┐
    │  碰撞  │──publish──►  │          │──dispatch──►  │ 音效 │
    └──────┘   channel      └──────────┘  channel      └──────┘
               "audio"                      "audio"
```

### 简单实现

```cpp
class MessageBus {
public:
    using Handler = std::function<void(const std::any&)>;  // or template<T>

    template<typename T>
    void subscribe(const std::string& channel, Handler h) {
        m_handlers[channel].push_back(std::move(h));
    }

    template<typename T>
    void publish(const std::string& channel, T&& msg) {
        for (auto& h : m_handlers[channel])
            h(msg);
    }

private:
    std::unordered_map<std::string, std::vector<Handler>> m_handlers;
};

// 用法
MessageBus bus;

bus.subscribe<CombatEvent>("combat", [](auto& e) {
    // UI 更新
});
bus.subscribe<CombatEvent>("combat", [](auto& e) {
    // 成就系统检查
});

bus.publish("combat", CombatEvent{playerId, enemyId, damage});
```

### 对比模式 ①

| | Event + Dispatcher (①) | Message Bus (⑤) |
|---|---|---|
| 类型安全 | 编译期 (`T::getStaticType()`) | 运行时（字符串 channel，`std::any` 擦除） |
| 发布者知道订阅者？ | 不关心 | 完全不知道 |
| 按类型路由 | ✅ | ❌（按字符串 channel） |
| 灵活性 | 低（新增事件 = 改代码） | 高（新 channel = 新字符串即可） |
| 性能 | 高（编译期） | 中等（字符串 hash + any cast） |

> ⚠️ Pub/Sub 是**最解耦**的模式，但也**最容易写出 spaghetti**——完全匿名的关系让调试变得困难。
> 适合「模块边界」级别的通信，不要用它替代所有 `std::function` 回调。

## ⑥ ECS 事件系统 (EnTT `dispatcher`)

**哲学：** 在 ECS 架构中，事件是 Systems 之间的通信方式。支持**立即触发**和**排队延迟**两种模式。

### EnTT dispatcher 核心 API

```cpp
// 创建一个 dispatcher（不需要任何基类！事件就是任意 struct）
entt::dispatcher dispatcher{};

// 连接：模板参数就是事件类型
dispatcher.sink<DamageEvent>().connect<&onDamage>();
dispatcher.sink<DeathEvent>().connect<&onDeath>();

// 立即触发（同步，handler 当场执行）
dispatcher.trigger(DamageEvent{entity, 42});

// 排队（异步，存入内部队列）
dispatcher.enqueue(DeathEvent{entity});
dispatcher.enqueue<CollisionEvent>(entityA, entityB);  // 就地构造

// 批量派发（主循环的固定时机调用）
dispatcher.update();  // 把所有排队事件一次性派发出去
```

### 关键设计决策

| 决策 | EnTT 的做法 |
|------|------------|
| 事件类型 | **任意类型**（`struct DamageEvent { Entity e; float amount; };`），不需要继承 |
| 类型识别 | `entt::type_info`（编译期 hash，比 `dynamic_cast` 快，比字符串安全） |
| 立即 vs 延迟 | 都支持：`trigger()` = 立即，`enqueue()` + `update()` = 延迟 |
| Handler 生命周期 | `sink` 返回连接对象，断开自动清理 |

### 完整示例

```cpp
struct CollisionEvent {
    entt::entity a, b;
};
struct DeathEvent {
    entt::entity who;
};

class CombatSystem {
    entt::dispatcher& m_dispatcher;
public:
    CombatSystem(entt::dispatcher& d) : m_dispatcher(d) {
        // 订阅碰撞事件
        m_dispatcher.sink<CollisionEvent>().connect<&CombatSystem::onCollision>(*this);
    }

    void onCollision(const CollisionEvent& e) {
        // ... 计算伤害
        if (dead) {
            // 不是直接调用 DeathSystem，而是发事件
            m_dispatcher.enqueue<DeathEvent>(e.a);
        }
    }
};

// 主循环
while (running) {
    physicsSystem.update();   // 物理系统 produce CollisionEvent
    dispatcher.update();      // ← 在这里统一派发所有排队事件
    renderSystem.update();
}
```

### 模式 ⑥ vs 模式 ①

| | Event + Dispatcher (①) | EnTT Dispatcher (⑥) |
|---|---|---|
| 事件需要基类？ | ✅ 必须继承 `Event` | ❌ 任意类型 |
| 新增事件开销 | 新类 + 新枚举值 + 宏 | 一个 struct |
| 延迟支持 | ❌（需外部 Queue） | ✅ 内置 `enqueue()` |
| ECS 集成 | 需桥接 | 原生 `entt::entity` 自然融入 |
| 反射/序列化 | 可以加（枚举助记） | 需额外的 `entt::meta` |
| 适合架构 | OOP | ECS |

## ⑦ 响应式 / Observable 流 (Reactive Programming)

**哲学：** 把事件看作**数据流**，可以用 `map`、`filter`、`merge`、`debounce` 等算子链式变换。

```
    原始事件流              变换                 消费
    ┌──────────┐     ┌──────────────┐      ┌──────────┐
    │ 按键事件  │──►  │ filter(ESC)  │──►   │ 关闭窗口  │
    │ 频发     │     │ debounce     │      │           │
    └──────────┘     │ (100ms)      │      └──────────┘
                     └──────────────┘
```

### 概念示例 (RxCpp 风格)

```cpp
// 玩家的经验值作为一个可观察属性
rxcpp::subjects::behavior<int> playerExp{0};

// 订阅：当经验值变化时自动计算等级并更新 UI
playerExp.get_observable()
    .map([](int exp) { return exp / 100; })        // 经验 → 等级
    .distinct_until_changed()                        // 等级不变不通知
    .subscribe([](int level) {
        ui.updateLevelDisplay(level);
    });

// 任何地方修改经验值，UI 自动更新
playerExp.get_subscriber().on_next(150);  // → level 1
playerExp.get_subscriber().on_next(250);  // → level 2
```

### 为什么游戏引擎很少全盘用这个？

| 优势 | 劣势 |
|------|------|
| 声明式，代码干净 | 分配开销（每个操作创建一个 observable 节点） |
| 自动传播变化 | 调试困难（堆栈不直观） |
| UI 绑定极好用 | 不适合每帧高频事件（鼠标移动 × 60fps） |

**游戏里最常见的使用场景：UI 数据绑定**（类似 Vue/React 的响应式），而不是替代核心事件系统。

## 如何选择？决策树

```
                          ┌─ 事件类型固定且有限？
                          │   ┌─ 需要延迟处理/录制回放？
                          │   │   └─ 模式 ④+①：EventQueue + Dispatcher
                          │   └─ 不需延迟 → 模式 ①：Event + Dispatcher
                          │
需要事件系统 ──┤   ┌─ 架构是 ECS？──→ 模式 ⑥：EnTT dispatcher
              │   │
              │   ├─ 需要跨模块、完全匿名通信？──→ 模式 ⑤：Message Bus
              │   │
              │   ├─ 需要反射/蓝图绑定？──→ 模式 ③：Unreal Delegates
              │   │
              │   ├─ 组件间松耦合点对点通知？──→ 模式 ②：Signal/Slot
              │   │
              │   └─ UI 数据绑定/属性监听？──→ 模式 ⑦：Observable
              │
              └─ 提示：这些模式不是互斥的。工业引擎通常是
                 **模式 ① 管输入事件 + 模式 ④ 做延迟 + 模式 ② 做模块间通信**
```

## 实战建议

### 对于你的引擎（当前阶段）

你已经在 [进阶 01](https://github.com/Tur/advanced/01-%E4%BA%8B%E4%BB%B6%E7%B3%BB%E7%BB%9F%E8%AE%BE%E8%AE%A1.md) 实现了**模式 ①**，这是一个很好的基础。接下来可以：

1. **全局事件总线**——在 `EventBus`（练习 3 的中间件链）之上加上**模式 ⑤** 的 channel 路由，让不同子系统不直接耦合
2. **事件队列**——给 Dispatcher 加一个 `enqueue()` / `process()` 层，把 GLFW 回调的事件先入队、再在固定时机派发（避免在物理计算中途修改状态）
3. **跨模块通信**——用轻量的 **Signal/Slot（模式 ②）**补充 Dispatcher，比如 `Signal<TextureHandle> onTextureLoaded`，不需要为此定义一个新的 Event 子类

### 不要做的事

- ❌ 不要为了「完整」把七种模式都塞进引擎——每加一种都要维护成本
- ❌ 不要用 Pub/Sub 替代所有直接调用——调试会变成噩梦
- ❌ 不要用 Observable 流处理每帧 60Hz 的鼠标移动——性能扛不住
