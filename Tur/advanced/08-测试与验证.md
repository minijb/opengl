# 进阶 08 · 测试与验证

> 目标：你说「不太会写 C++ 的测试」——这篇就是写给你的。从零开始：选框架、配 CMake、写第一个测试，
> 然后把我们前面写的事件系统、输入状态表、窗口逻辑都测一遍。
> 核心信念：**好抽象 = 好测试**。你前面做的事件系统、Input 状态表之所以能测，正是因为我们把纯逻辑从 GL/窗口里剥了出来。

---

## 8.1 先建立认知：什么能测，什么不能

图形程序测试最大的误区是「窗口没法测，所以啥都不测」。其实大部分逻辑是**纯逻辑**，不需要窗口：

| 代码 | 需要窗口/显卡吗？ | 好测吗 |
|---|---|---|
| `EventDispatcher` 按类型派发 | ❌ 纯逻辑 | ✅ 极好测 |
| `Event` 分类位掩码 `isInCategory` | ❌ | ✅ |
| Input 的 `keyJustPressed` 边沿检测 | ❌（只依赖 current/previous 两张表） | ✅ |
| `KeyCode` 映射 `toGlfwKey` | ❌ | ✅ |
| `WindowProps` 默认值 | ❌ | ✅ |
| `glfwCreateWindow` 本身 | ✅ 要显示 | 难（用 fake 替代） |
| `glDrawArrays` 渲染正确性 | ✅ 要 GPU | 难（渲染测试是另一门学问） |

**结论**：把纯逻辑剥干净（这正是 [01 篇](01-事件系统设计.md) 事件系统、[03 篇](03-输入系统.md) Input 状态表做的事），
就能写一堆又快又稳的单元测试；剩下非要窗口的部分，用 fake（[02 篇练习 3](02-窗口抽象层与接口设计.md) 的 `HeadlessWindow`）顶替。

## 8.2 选框架：doctest（单文件，最适合本项目）

C++ 测试框架三巨头：

| 框架 | 特点 | 适合 |
|---|---|---|
| **GoogleTest** | 功能全、生态大 | 大型工程，要 mock 框架 |
| **Catch2** | 单头（v2）/ 多文件（v3），宏友好 | 中型工程 |
| **doctest** | 单头、编译**最快**、宏极简 | 中小型工程、教学 ✅ |

本仓库依赖全是**源码 vendoring**（`lib/glfw`、`lib/glew`、`lib/glm`），所以用单头的 doctest 最一致——
下载一个 `doctest.h` 丢进 `lib/doctest/` 即可，零额外构建。

> 💡 你后面想换 GoogleTest 完全没问题，测试**思想**（AAA、断言、独立性）跨框架通用。先从 doctest 起步最快。

## 8.3 接入 CMake（与现有依赖一致）

### 第 1 步：拿 doctest

下载 `doctest.h`（单文件，~1MB）放进 `lib/doctest/doctest.h`。
（或用 FetchContent 自动拉，但 vendoring 和你现有风格一致。）

### 第 2 步：CMake 加一个测试目标

在 `CMakeLists.txt` 末尾追加：

```cmake
# —— 测试 ——
enable_testing()

add_executable(tests
    test/test_main.cpp          # doctest 入口
    test/test_events.cpp        # 事件系统测试
    test/test_input.cpp         # 输入状态表测试
)
target_include_directories(tests PRIVATE
    src                         # 测你 src/ 里的代码
    lib/doctest                 # doctest.h
)
# 如果你的核心逻辑已经拆成库，就 link 它：
# target_link_libraries(tests PRIVATE engine_core)
doctest_discover_tests(tests)   # 让 ctest 自动发现每个 TEST_CASE
```

> ⚠️ `doctest_discover_tests` 需要 doctest 的 CMake helper。最省事的替代：直接 `add_test(NAME tests COMMAND tests)`，
> 不做单用例发现也能跑（只是 ctest 不分粒度）。

### 第 3 步：测试入口

```cpp
// test/test_main.cpp
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN   // 让 doctest 生成 main()
#include <doctest.h>
```

有这一行就够了，`main` 自动生成。直接编译运行 `tests` 即可。

## 8.4 第一个测试：AAA 模式

每个测试都遵循 **AAA**：

- **Arrange**（准备）：构造输入和预期。
- **Act**（执行）：调用被测函数。
- **Assert**（断言）：检查结果。

```cpp
// test/test_main.cpp（先写个最简单的，确认能跑）
#define DOCTEST_CONFIG_IMPLEMENT_WITH_MAIN
#include <doctest.h>

TEST_CASE("一个最简单的测试：加法") {
    // Arrange
    int a = 2, b = 3;
    int expected = 5;
    // Act
    int result = a + b;
    // Assert
    CHECK(result == expected);
}
```

编译运行：

```bash
cmake -B build && cmake --build build
./build/tests            # 跑全部测试
./build/tests --help     # doctest 自带命令行选项
```

看到 `1 test case passed` 就成功了。这就是 C++ 测试的全部骨架。

> 💡 命名建议：`TEST_CASE("被测对象: 行为描述")`，例如 `"EventDispatcher: 只派发匹配类型"`。
> 一眼看出在测什么、出了什么问题。

## 8.5 给事件系统写测试

测 [01 篇](01-事件系统设计.md) 的 `EventDispatcher` 和事件类。这些都是纯逻辑，不需要窗口。

```cpp
// test/test_events.cpp
#include <doctest.h>
#include "Event.h"          // 你 src/ 里的事件定义

TEST_CASE("WindowResizeEvent: 携带正确的尺寸") {
    // Arrange
    WindowResizeEvent e(1920, 1080);
    // Act + Assert
    CHECK(e.getWidth()  == 1920);
    CHECK(e.getHeight() == 1080);
    CHECK(e.getEventType() == EventType::WindowResize);
    CHECK(e.isInCategory(EventCategory::Application));
    CHECK_FALSE(e.isInCategory(EventCategory::Keyboard));   // 不属于键盘类
}

TEST_CASE("EventDispatcher: 只派发匹配类型") {
    // Arrange
    WindowResizeEvent e(800, 600);
    EventDispatcher dispatcher(e);
    bool resizeCalled = false;
    bool keyCalled = false;

    // Act：注册两个 handler，但事件是 WindowResize
    dispatcher.dispatch<WindowResizeEvent>([&](WindowResizeEvent& ev) {
        resizeCalled = true;
        CHECK(ev.getWidth() == 800);
        return true;
    });
    dispatcher.dispatch<KeyPressedEvent>([&](KeyPressedEvent&) {
        keyCalled = true;       // 不应该被调到
        return false;
    });

    // Assert
    CHECK(resizeCalled);
    CHECK_FALSE(keyCalled);
}

TEST_CASE("EventDispatcher: handled 标志阻止传播") {
    // Arrange
    KeyPressedEvent e(65 /*A*/, 0);
    EventDispatcher dispatcher(e);

    // Act：第一个 handler 标记已处理
    dispatcher.dispatch<KeyPressedEvent>([](KeyPressedEvent&) { return true; });

    // Assert
    CHECK(e.handled == true);   // 后续 handler 应据此跳过
}
```

这几行就覆盖了事件系统的核心行为：类型匹配、数据正确、传播控制。**秒级跑完，不需要显卡。**

## 8.6 给 Input 状态表写测试（重点：纯逻辑）

[03 篇 3.5 节](03-输入系统.md) 的 `keyJustPressed` 依赖 `s_currentState` / `s_previousState` 两张表。
把「给定两张表，返回是否 justPressed」抽成纯函数，就能不碰窗口地测：

```cpp
// src/InputLogic.h  （把判定逻辑抽成无状态函数，方便测）
enum class KeyCode { A = 0 /*...*/ };
inline bool justPressed(bool current, bool previous) {
    return current && !previous;
}

// test/test_input.cpp
#include <doctest.h>
#include "InputLogic.h"

TEST_CASE("justPressed: 边沿检测四种情况") {
    // Arrange + Act + Assert，每种状态组合一例
    CHECK(justPressed(true,  false) == true);    // 上帧没按、本帧按 → 刚按下 ✅
    CHECK(justPressed(true,  true)  == false);   // 一直按着 → 不是“刚”
    CHECK(justPressed(false, true)  == false);   // 上帧按、本帧松 → 是 justReleased，不是 justPressed
    CHECK(justPressed(false, false) == false);   // 一直没按
}

TEST_CASE("Input: 模拟一次“按下→松开”的帧序列") {
    // Arrange：用数组模拟连续几帧的按键状态
    bool sequence[] = { false, true, true, true, false };
    bool prev = false;
    int justPressedCount = 0;

    // Act：遍历帧序列，数 justPressed 触发次数
    for (bool cur : sequence) {
        if (justPressed(cur, prev)) justPressedCount++;
        prev = cur;
    }

    // Assert：整个序列里“刚按下”只该触发一次
    CHECK(justPressedCount == 1);
}
```

第二个测试验证了一个**跨帧的不变量**：无论按住多久，「刚按下」只触发一次。这种「行为测试」比单点断言更有价值——
它测的是 `nextFrame()` 时机正确的逻辑后果（[03 篇](03-输入系统.md) 强调过的点）。

> 💡 这就是为什么 [03 篇](03-输入系统.md) 要把状态表和 GLFW 分开——分开后这段逻辑是纯函数，几行就能测。

## 8.7 用 HeadlessWindow 测窗口侧逻辑（Fake，不是 Mock）

[02 篇练习 3](02-窗口抽象层与接口设计.md) 让你写过一个 `HeadlessWindow`（不依赖任何窗口库，`pollEvents/swapBuffers` 全空）。
它的真正用途就是**测试替身**：

```cpp
// test/HeadlessWindow.h
#include "Window.h"
class HeadlessWindow : public Window {
    bool m_shouldClose{false};
    int m_w, m_h;
    EventCallback m_cb;
public:
    bool init(const Props& p) override { m_w = p.width; m_h = p.height; return true; }
    void shutdown() override {}
    void pollEvents() override {}
    void swapBuffers() override {}
    bool shouldClose() const override { return m_shouldClose; }
    void setShouldClose(bool v) override { m_shouldClose = v; }
    int width() const override { return m_w; }
    int height() const override { return m_h; }
    void setVsync(bool) override {}
    void setEventCallback(EventCallback cb) override { m_cb = std::move(cb); }

    // 测试辅助：手动“合成”一个事件喂进去
    void simulateEvent(Event& e) { if (m_cb) m_cb(e); }
};
```

用它测「应用层逻辑」，而不碰真窗口：

```cpp
TEST_CASE("Application: 按 ESC 设置 shouldClose") {
    // Arrange
    HeadlessWindow window;
    window.init({});
    window.setEventCallback([&](Event& e){
        EventDispatcher d(e);
        d.dispatch<KeyPressedEvent>([&](KeyPressedEvent& ev){
            if (ev.getKeyCode() == 65 /*A, 当作 ESC 替身*/) window.setShouldClose(true);
            return true;
        });
    });

    // Act：模拟一次按键
    KeyPressedEvent fakeKey(65, 0);
    window.simulateEvent(fakeKey);

    // Assert
    CHECK(window.shouldClose() == true);
}
```

这里 `HeadlessWindow` 是 **Fake**：一个简化但真实可用的实现。它实现了 `Window` 接口的全部行为，
只是不画图、不连操作系统。区别于 **Mock**：

- **Fake**：手写一个轻量真实现（`HeadlessWindow`）。推荐，C++ 里最自然。
- **Mock**：用框架（gmock）自动生成，记录「哪个方法被调了几次」。重，图形程序很少需要。

> 💡 C++ 图形/引擎测试**几乎都用 Fake，不用 Mock**。别一上来就学 gmock 的 `EXPECT_CALL`——
> 大多数时候一个 50 行的 `HeadlessWindow` 比一堆 mock 期望清晰得多。

## 8.8 运行、CI 与测试习惯

### 日常运行

```bash
./build/tests                 # 全跑，几毫秒出结果
./build/tests "EventDispatcher"   # 只跑名字匹配的用例
ctest --test-dir build        # 走 CMake 的测试入口
```

doctest 输出极简洁：失败会精确到文件行号 + 表达式 + 实际值。

### CI（持续集成）

把测试加进 CI 脚本，每次 push 自动跑。GitHub Actions 示例（`.github/workflows/test.yml`）：

```yaml
name: tests
on: [push, pull_request]
jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - uses: actions/checkout@v4
        with: { submodules: true }
      - run: cmake -B build -DCMAKE_BUILD_TYPE=Debug
      - run: cmake --build build
      - run: ctest --test-dir build --output-on-failure
```

CI 服务器无显示器，**正是 Fake 的用武之地**——`HeadlessWindow` 让事件/输入/应用逻辑在无显卡环境照样测。

### 测试习惯（比工具更重要）

1. **测行为，不测实现**：测「按 ESC 会关窗」，不测「`m_shouldClose` 被赋值为 true」。
   后者换实现就坏，是脆弱测试。
2. **一个 TEST_CASE 测一件事**：失败时一眼知道哪里坏了。
3. **AAA 分段写**，读的人（包括半年后的你）能立刻看清意图。
4. **先测再改（回归测试）**：修 bug 前，先写一个**能复现 bug** 的测试（红），再改代码让它变绿。
   这样 bug 永远不会复发。
5. **不测 GL 渲染结果**：渲染正确性靠眼睛 + RenderDoc，单元测试不该断言像素颜色（脆且慢）。

## 8.9 小结

- **可测性是抽象的回报**：事件系统、Input 状态表能测，是因为我们把纯逻辑从 GL/窗口里剥了出来。
- **doctest** 单头最快起步，AAA 模式 + `CHECK` 是全部骨架。
- **测纯逻辑**（事件派发、边沿检测、键码映射），**用 Fake 测窗口侧**（`HeadlessWindow`），
  **不测渲染像素**。
- **Fake > Mock**：C++ 引擎测试几乎都用 Fake，别急着上 gmock。
- **先写复现测试再修 bug**——这是测试最实用的姿势。

TEST_CASE("MouseMovedEvent: 携带坐标与分类") {
    MouseMovedEvent e(128.f, 256.f);

### 2. `keyJustPressed` 纯函数 + 帧序列测试（含「写错看它红」）

```cpp
// InputLogic.h
inline bool justPressed(bool current, bool previous) { return current && !previous; }

// test_input.cpp
TEST_CASE("justPressed: 四种状态组合") {
    CHECK(justPressed(true,  false) == true);
    CHECK(justPressed(true,  true)  == false);
    CHECK(justPressed(false, true)  == false);
    CHECK(justPressed(false, false) == false);
}
TEST_CASE("按下→松开序列: justPressed 只触发一次") {
    bool seq[] = { false, true, true, true, false }; bool prev = false; int cnt = 0;
    for (bool cur : seq) { if (justPressed(cur, prev)) ++cnt; prev = cur; }
    CHECK(cnt == 1);
}
// 故意写错版：inline bool justPressedBad(bool c, bool p){ return c; }  ← 去掉 !p
// 第二个测试 cnt 会变成 4（红），改对后变回 1（绿）→ 体会先红后绿。
```

### 3. `HeadlessWindow` + 按键帧序列测试

```cpp
TEST_CASE("Application: 连续按键 → 松开，状态正确切换") {

    w.setEventCallback([&](Event& e){
        EventDispatcher d(e);
        d.dispatch<KeyPressedEvent>([&](auto&){ paused = !paused; return true; });

    KeyPressedEvent p2(65, 0); w.simulateEvent(p2);  CHECK(paused == false);
}
```
