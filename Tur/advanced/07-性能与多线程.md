# 进阶 07 · 性能与多线程

> 目标：窗口子系统能跑起来后，迟早要面对两个工程问题——「卡顿怎么定位」和「能不能用多线程」。
> 本篇讲清楚实时渲染的性能思维、帧时间、固定步长、VSync 的代价，以及 OpenGL + GLFW 下的多线程硬规则和实用模式。
> 不堆理论，每条都给可落地的代码。

---

## 7.1 性能第一原则：先测后优

> 「过早优化是万恶之源。」——Knuth

性能问题的头号陷阱是「凭感觉优化」。一个 60FPS 的程序，到底是 CPU 卡、GPU 卡、驱动卡、还是 IO 卡？
不看数据瞎优化，往往优化了不卡的函数。

正确流程：

```
测（profiler / 计时）→ 定位最慢的那一段 → 只优化那一段 → 再测验证
```

工具：
- **RenderDoc**：逐 draw call 看 GPU 状态，定位渲染瓶颈（过度绘制、shader 复杂度）。
- **Tracy / Optick**：CPU + GPU 帧级 profiler，看每帧时间花在哪。
- **编译器 sanitizer**：`-fsanitize=address,undefined`，定位内存和 UB（见 7.9）。
- **手写计时**：`std::chrono`，最简单的兜底（下面 7.2 给代码）。

## 7.2 帧时间 vs FPS：用毫秒，别用帧率

新手爱说「我的程序跑 60 帧」，但帧率（FPS）是**非线性**的，不适合做性能推理：

```
60 FPS = 16.6 ms/帧
30 FPS = 33.3 ms/帧   ← 掉了一半帧率，但每帧多花 16.7 ms
20 FPS = 50.0 ms/帧
```

从 60 掉到 50 FPS（每帧 16.6→20ms，多了 3.4ms）和从 30 掉到 20 FPS（33.3→50ms，多了 16.7ms），
看着都是「掉 10 帧」，实际代价差 5 倍。**永远用「每帧多少毫秒」衡量。**

最小计时工具：

```cpp
#include <chrono>
using Clock = std::chrono::high_resolution_clock;

class Timer {
public:
    void update() {
        auto now = Clock::now();
        using MS = std::chrono::duration<float, std::milli>;
        m_deltaMs = std::chrono::duration_cast<MS>(now - m_last).count();
        m_last = now;
    }
    float deltaMs() const { return m_deltaMs; }
    float deltaSeconds() const { return m_deltaMs / 1000.0f; }
private:
    Clock::time_point m_last{Clock::now()};
    float m_deltaMs{0.0f};
};
```

主循环里：

```cpp
Timer timer;
while (!window.shouldClose()) {
    timer.update();
    float dt = timer.deltaSeconds();   // 这一帧的真实耗时（秒）
    update(dt);
    render();
    window.swapBuffers();
    window.pollEvents();
}
```

> 💡 在 ImGui 里画一条 `dt` 的折线图（`ImGui::PlotLines`），卡顿那一帧会冒尖——比看 FPS 数字直观得多。

## 7.3 固定步长：物理要稳，渲染要顺

**可变步长**（上一节的 `dt`）：每帧用真实耗时更新逻辑。简单，但物理积分会不稳——`dt` 忽大忽小，
物体速度会「抖」。

**固定步长**：逻辑以恒定 `dt`（如 1/60s）推进，渲染插值。经典做法是 **accumulator（累加器）模式**：

```cpp
const float FIXED_DT = 1.0f / 60.0f;   // 物理步长
float accumulator = 0.0f;
Timer timer;

while (!window.shouldClose()) {
    timer.update();
    accumulator += timer.deltaSeconds();

    // 防止卡顿后累加太多导致「死循环」（比如断点停了很久）
    if (accumulator > 0.25f) accumulator = 0.25f;

    while (accumulator >= FIXED_DT) {
        physicsUpdate(FIXED_DT);       // ← 恒定步长，物理稳定
        accumulator -= FIXED_DT;
    }

    float alpha = accumulator / FIXED_DT;   // 插值因子 0~1
    render(alpha);                           // 渲染时在两个物理帧间插值
    window.swapBuffers();
    window.pollEvents();
}
```

规则：
- **物理 / 游戏逻辑**：固定步长，确定性可复现，适合网络同步和回放。
- **渲染 / 输入采样**：可变步长，跟显示器走。
- 卡顿时内层 `while` 多跑几次物理追上实时；极端卡顿（断点）用 `accumulator` 上限兜底。

> 💡 这就是《Fix Your Timestep!》（Glenn Fiedler）那篇经典文章讲的东西，强烈推荐读原文。

## 7.4 VSync 的两面性

`glfwSwapInterval(1)` 让 swap 等垂直同步信号，好处是帧率稳定、不撕裂；
**代价是输入延迟**：你这一帧画完了，得等下一个同步信号才能上屏，多等 0~16ms。

对竞速、FPS 这类低延迟需求，引擎常做：
- **VSync 关** + 自己限帧（`std::this_thread::sleep_until` 算好的下一帧时间）→ 延迟比纯 VSync 低。
- **三缓冲**：驱动层面让渲染不阻塞，延迟介于两者之间。

简单限帧示例：

```cpp
const double TARGET_FPS = 144.0;
const double FRAME_TIME = 1.0 / TARGET_FPS;

auto frameStart = Clock::now();
while (!window.shouldClose()) {
    // ... update + render + swap + poll

    auto frameEnd = frameStart + std::chrono::duration<double>(FRAME_TIME);
    std::this_thread::sleep_until(frameEnd);
    frameStart = frameEnd;
}
```

别无脑关 VSync 追求高帧率——超过显示器刷新率的部分全是浪费，还撕裂。先测延迟再决定。

## 7.5 多线程的硬规则（GLFW + OpenGL）

在写任何多线程代码前，先记住三条**不可违反**的规则：

1. **窗口相关的 GLFW 调用必须在主线程**（精确规则见 [06 篇 6.6 节](06-多窗口与生命周期管理.md)）。
   - 初始化/终止、创建窗口、注册回调、`pollEvents` 都在主线程。
   - 官方允许任意线程的只有一小撮：`glfwPostEmptyEvent()`（唤醒阻塞中的 `glfwWaitEvents()`）、
     `glfwMakeContextCurrent`、`glfwSwapBuffers`/`glfwSwapInterval`、计时函数与 Vulkan 查询。
2. **一个 OpenGL 上下文同一时刻只能 current 在一个线程**。
   - 线程 A `makeCurrent(ctx)` 后，线程 B 不能再 `makeCurrent(ctx)`，要先在 A 上释放。
   - GL 调用只对「当前线程的当前上下文」生效。
3. **GL 对象（纹理、buffer、shader）属于创建它的上下文**。
   - 跨上下文共享要显式建「共享上下文」（见 [06 篇 6.5 节](06-多窗口与生命周期管理.md)），且要同步。

推论：**多窗口 ≠ 多线程**（[06 篇 6.6 节](06-多窗口与生命周期管理.md) 提过）。多窗口是「多个上下文轮流 current 在主线程」。
真正的多线程渲染有专门架构（7.8）。

## 7.6 异步资源加载（最常用的多线程）

加载一个 4K 贴图：磁盘读 + PNG/JPEG 解码可能要几十毫秒。**在主线程做 → 卡顿掉帧。**

正确拆分：**CPU 活儿放工作线程，GL 活儿放主线程**（因为 GL 上传要在主线程的上下文上）。

```cpp
struct LoadedImage {
    int w, h, channels;
    std::vector<unsigned char> pixels;
};

// 工作线程：只做 CPU 工作（读文件 + 解码），不碰任何 GL
std::future<LoadedImage> loadAsync(const std::string& path) {
    return std::async(std::launch::async, [path]() {
        LoadedImage img;
        // stbi_load / 你的解码库，纯 CPU
        // img.pixels = decode(readFile(path));
        return img;
    });
}

// 主线程：拿到解码结果后，上传成 GL 纹理
void mainThreadUpload(std::future<LoadedImage>& fut) {
    if (fut.valid() &&
        fut.wait_for(std::chrono::seconds(0)) == std::future_status::ready) {
        LoadedImage img = fut.get();
        GLuint tex;
        glGenTextures(1, &tex);                       // ← GL 调用，必须在主线程
        glBindTexture(GL_TEXTURE_2D, tex);
        glTexImage2D(GL_TEXTURE_2D, 0, GL_RGBA,
                     img.w, img.h, 0, GL_RGBA, GL_UNSIGNED_BYTE, img.pixels.data());
    }
}
```

要点：
- 工作线程**绝不**调 `glXxx`——会崩或静默失败。
- 主线程**轮询** `future`（`wait_for(0)`），ready 了才上传，否则跳过这一帧。
- 加载完的纹理通过一个「待上传队列」交接（见 7.7 的线程安全队列）。

> 💡 进阶：用**共享上下文**让工作线程也能上传纹理。但共享上下文要 GL 同步（fence），复杂度高一截。
> 新手先用「工作线程解码 + 主线程上传」这个稳的方案。

## 7.7 线程安全的状态共享

多线程下，共享数据要么加锁，要么用原子。窗口子系统常见的几类：

### 单个数值（鼠标坐标、帧计数）→ `std::atomic`

```cpp
std::atomic<float> mouseX{0}, mouseY{0};
// 事件回调（主线程）写：
mouseX.store(ev.x, std::memory_order_relaxed);
// 渲染线程读：
float x = mouseX.load(std::memory_order_relaxed);
```

单个标量用 atomic，无锁、够快。

### 一帧的快照 → 双缓冲（double buffering）

渲染线程要用「一整帧的输入状态」，逐个 atomic 读会有撕裂（读到一半被改）。用双缓冲：

```cpp
struct InputSnapshot {
    std::array<bool, 256> keys;
    float mouseX, mouseY;
};

class InputBuffer {
    InputSnapshot m_snapshots[2];
    std::atomic<int> m_writeIndex{0};   // 主线程写哪个
public:
    // 主线程（每帧）：写入非活跃缓冲，然后翻转
    void publish(InputSnapshot snap) {
        int wi = m_writeIndex.load();
        m_snapshots[wi ^ 1] = std::move(snap);
        m_writeIndex.store(wi ^ 1);     // 原子翻转
    }
    // 渲染线程：读活跃缓冲（拿到的始终是一致的整帧）
    const InputSnapshot& read() const {
        return m_snapshots[m_writeIndex.load()];
    }
};
```

写线程写「另一块」再原子翻转指针，读线程永远读到一块完整的旧帧——无锁且一致。

### 任务队列 → mutex + condition_variable

异步加载、渲染命令队列都用这个经典结构：

```cpp
#include <mutex>
#include <condition_variable>
#include <queue>

template<typename T>
class ConcurrentQueue {
public:
    void push(T item) {
        { std::lock_guard lk(m_mutex);
          m_queue.push(std::move(item)); }
        m_cv.notify_one();
    }
    T pop() {
        std::unique_lock lk(m_mutex);
        m_cv.wait(lk, [&]{ return !m_queue.empty(); });   // 空就等
        T item = std::move(m_queue.front());
        m_queue.pop();
        return item;
    }
private:
    std::mutex m_mutex;
    std::condition_variable m_cv;
    std::queue<T> m_queue;
};
```

`push` 加锁塞入并通知，`pop` 加锁、队列空就 `wait`（不空忙转）。生产者—消费者的标准骨架。

## 7.8 渲染线程架构（进阶）

把渲染从主线程搬到独立线程，是大型引擎（Unreal、Unity SRP）的做法。核心是**命令缓冲（command buffer）队列**：

```
主线程（游戏逻辑）            渲染线程（GL 调用）
  update()                       while (running) {
  构建 RenderCommand ──入队──►     cmd = queue.pop()
  （不碰 GL）                     执行 cmd（glDrawXXX 等）
                                  swapBuffers
                                }
```

- 主线程只生成「画什么」的指令（哪个 shader、哪些 uniform、哪个 VAO），不调 GL。
- 渲染线程消费指令、真正调 GL，独占上下文。
- 两者通过 7.7 的并发队列 + 双缓冲交接。

好处：游戏逻辑和渲染并行，主线程被渲染阻塞的时间消失。
代价：复杂、要处理帧间依赖、GL 同步。**新手不建议上来就做**——先单线程跑顺，profiler 证明渲染是瓶颈再上。

## 7.9 实用工具与排错

| 工具 | 用途 |
|---|---|
| `-fsanitize=address` | 内存越界、use-after-free，定位 90% 的崩溃 |
| `-fsanitize=thread` (TSan) | 数据竞争检测（多线程必用） |
| `-fsanitize=undefined` | 未定义行为（整数溢出、空指针解引用） |
| RenderDoc | GPU 逐 draw call 调试 |
| Tracy / Optick | 帧级 CPU+GPU profiler |
| `std::thread::hardware_concurrency()` | 查 CPU 核心数，决定线程池大小 |

CMake 里给 Debug 开 sanitizer：

```cmake
if(CMAKE_BUILD_TYPE STREQUAL "Debug")
    add_compile_options(-fsanitize=address,undefined -fno-omit-frame-pointer)
    add_link_options(-fsanitize=address,undefined)
endif()
```

> ⚠️ ASan 和 TSan **不能同时开**（互斥）。测内存用 ASan，测多线程用 TSan，分开跑。
>
> ⚠️ 上面是 GCC/Clang 的写法。MSVC 用 `/fsanitize=address`；且 VS / Ninja Multi-Config 这类多配置生成器里
> `CMAKE_BUILD_TYPE` 为空，上面的 `STREQUAL "Debug"` 判断永远不成立——要按配置生效，请用生成器表达式
> （如 `$<$<CONFIG:Debug>:/fsanitize=address>`）或直接加进 `CMAKE_CXX_FLAGS_DEBUG`。

多线程最常见 bug：**忘了加锁导致数据竞争**——程序时好时坏、换个机器就崩。TSan 能在测试时揪出来，
别等线上随机崩溃。

## 7.10 小结

- 性能：**用帧时间（ms）不用 FPS**，先 profiler 定位再优化，别凭感觉。
- 时步：**物理用固定步长（accumulator），渲染/输入用可变步长**。
- VSync：稳帧但加延迟，竞速类可关 VSync + 自己限帧。
- 多线程三条铁律：GLFW 只在主线程、一个上下文只 current 在一个线程、GL 对象归属上下文。
- 实用模式：**异步资源加载**（worker 解码 + 主线程上传）、**双缓冲快照**、**mutex+CV 队列**。
- 渲染线程是进阶，profiler 证明需要再上。

### 3. `std::atomic` 帧计数器（TSan 验证）

```cpp
std::atomic<long long> frameCounter{0};
std::thread logic([&]{ while (running) { /* update */ frameCounter.fetch_add(1, std::memory_order_relaxed); } });
std::thread render([&]{ while (running) { /* draw */  frameCounter.fetch_add(1, std::memory_order_relaxed); } });
// 编译加 -fsanitize=thread，TSan 不报警 = 无数据竞争
```

### 4.（进阶）SPSC 渲染命令队列（先不接 GL）

```cpp
template<typename T>
class SPSCQueue {
    std::queue<T> m_q; std::mutex m_mtx; std::condition_variable m_cv; bool m_stop{false};
public:
    void push(T x) {
        { std::lock_guard lk(m_mtx); m_q.push(std::move(x)); }
        m_cv.notify_one();
    }
    std::optional<T> pop() {
        std::unique_lock lk(m_mtx);
        m_cv.wait(lk, [&]{ return m_stop || !m_q.empty(); });
        if (m_stop && m_q.empty()) return std::nullopt;
        T x = std::move(m_q.front()); m_q.pop();
        return x;
    }
    void stop() { { std::lock_guard lk(m_mtx); m_stop = true; } m_cv.notify_one(); }
};
// 主线程 push({Draw, VAO, ...})；消费线程 pop() 后 std::cout 打印指令
```
