# 进阶 02 · 窗口抽象层与接口设计

> 目标：到目前为止，`GLFWManager` 已经把 GLFW 藏在 `.cpp` 里了——但它毕竟还**叫** `GLFWManager`，
> 引擎核心还是知道「我用的是 GLFW」。本篇把它升级成纯虚接口 `Window`，让核心代码连 GLFW 这个名字都不认识。
> 换窗口库时，引擎核心零改动。

---

## 2.1 为什么要再抽象一层？

[基础篇 04](../basics/04-实现基础GLFWManager.md) 的 `GLFWManager` 已经不错，但还有两个不够：

1. **名字泄露意图**：核心代码 `#include "GLFWManager.h"`、`GLFWManager window;`——一看就知道是 GLFW。
   想换 SDL2？得全局改名、改 include。
2. **直接依赖具体类**：核心持有 `GLFWManager` 实例，等于和 GLFW 二进制绑死。

理想状态：引擎核心只认识一个抽象概念「**Window**」，至于这个 Window 背后是 GLFW、SDL 还是 Win32，核心不关心，
由一个工厂在「边界」处决定。

```
引擎核心层 (core)
   ├── 只 #include "Window.h"        ← 纯虚接口
   ├── 只持有 Window* / unique_ptr<Window>
   └── 不知道 GLFW 存在
         │
         ▼  (工厂在 platform 层创建)
平台层 (platform)
   ├── GLFWWindowImpl : public Window   ← GLFW 实现
   └── (未来) SDLWindowImpl : public Window
```

这就是**依赖倒置原则（DIP）**：核心定义接口，平台实现接口，依赖方向从「核心→平台」反过来变成「平台→核心」。

---

## 2.2 第一步：纯虚接口 `Window`

```cpp
// Window.h   （放在 core 层，不依赖任何窗口库）
#pragma once
#include <memory>
#include <string>
#include "Event.h"   // 用 [01 篇](01-事件系统设计.md) 的事件系统

class Window {
public:
    struct Props {
        std::string title{"OpenGL App"};
        int  width {800};
        int  height{600};
        bool fullscreen{false};
        bool vsync     {true};
    };

    using EventCallback = std::function<void(Event&)>;

    virtual ~Window() = default;

    virtual bool init(const Props& props = {}) = 0;
    virtual void shutdown() = 0;

    // 主循环
    virtual void pollEvents() = 0;
    virtual void swapBuffers() = 0;
    virtual bool shouldClose() const = 0;
    virtual void setShouldClose(bool v) = 0;

    // 属性
    virtual int  width() const = 0;
    virtual int  height() const = 0;
    virtual void setVsync(bool enabled) = 0;
    virtual void setEventCallback(EventCallback cb) = 0;

    // 工厂：核心代码通过这个函数拿窗口，不知道具体类型
    static std::unique_ptr<Window> create(const Props& props = {});
};
```

要点：
- **全是纯虚函数**（`= 0`），`Window` 本身不可实例化。
- **虚析构 `= default`**：通过基类指针 delete 派生类对象时必须虚析构，否则 UB。
- **`static create()` 工厂**：核心代码调 `Window::create({...})` 拿到一个 `unique_ptr<Window>`，
  具体是哪种实现，由工厂内部决定——核心根本不需要知道。

> 💡 这就是**工厂方法模式**。把「对象构造」和「对象使用」分离：使用方只面向接口。

## 2.3 第二步：GLFW 实现

把原来的 `GLFWManager` 改造成 `GLFWWindowImpl`，继承 `Window`：

```cpp
// GLFWWindowImpl.h   （放在 platform 层）
#pragma once
#include "Window.h"

struct GLFWwindow;   // 仍然前向声明

class GLFWWindowImpl : public Window {
public:
    GLFWWindowImpl() = default;
    ~GLFWWindowImpl() override;

    bool init(const Props& props) override;
    void shutdown() override;

    void pollEvents() override;
    void swapBuffers() override;
    bool shouldClose() const override;
    void setShouldClose(bool v) override;

    int  width() const override  { return m_width; }
    int  height() const override { return m_height; }
    void setVsync(bool enabled) override;
    void setEventCallback(EventCallback cb) override { m_eventCb = std::move(cb); }

private:
    static void keyCallback(GLFWwindow* w, int key, int sc, int action, int mods);
    static void framebufferSizeCallback(GLFWwindow* w, int width, int height);
    // ...其它 GLFW 回调

    GLFWwindow*   m_window{nullptr};
    int           m_width{0}, m_height{0};
    EventCallback m_eventCb;
};
```

`.cpp` 的实现和 [基础篇 04](../basics/04-实现基础GLFWManager.md) 的 `GLFWManager.cpp` **几乎一模一样**，
只是把类名换成 `GLFWWindowImpl`、回调改成喂 `Event`（[01 篇](01-事件系统设计.md) 的做法）。这里不重复贴。

## 2.4 第三步：工厂的实现（在平台层，隔离 GLFW 依赖）

```cpp
// Window.cpp   （注意：这个 .cpp 放在 platform 层，include GLFWWindowImpl.h）
#include "Window.h"
#include "GLFWWindowImpl.h"

std::unique_ptr<Window> Window::create(const Props& props) {
    auto window = std::make_unique<GLFWWindowImpl>();
    if (!window->init(props)) return nullptr;   // 创建失败返回空，调用方自行处理
    return window;
}
```

> ⚠️ 工厂的**实现**必须能看见 `GLFWWindowImpl` 的完整定义，所以 `Window.cpp` 在 platform 层、include 了 GLFW。
> 但 `Window.h`（接口）本身在 core 层、零 GLFW 依赖。**依赖只存在于 .cpp，不存在于头**——这是关键。

也可以用「条件编译」在编译期切后端：

```cpp
std::unique_ptr<Window> Window::create(const Props& props) {
#if defined(USE_GLFW)
    return std::make_unique<GLFWWindowImpl>(props);
#elif defined(USE_SDL)
    return std::make_unique<SDLWindowImpl>(props);
#else
    #error "No window backend selected"
#endif
}
```

CMake 里 `target_compile_definitions(MyEngine PUBLIC USE_GLFW)` 选后端，核心代码一个字不改。

## 2.5 引擎核心怎么用（彻底干净）

```cpp
// Application.h   （core 层）
#include "Window.h"
class Application {
    std::unique_ptr<Window> m_window;
};

// Application.cpp
Application::Application() {
    m_window = Window::create({ "My Engine", 1280, 720 });
    m_window->setEventCallback([this](Event& e){ this->onEvent(e); });
}

void Application::run() {
    while (!m_window->shouldClose()) {
        render();
        m_window->swapBuffers();
        m_window->pollEvents();
    }
}
```

整个 `Application` 看不到 `GLFW`、`SDL` 任何字眼。这就是引擎核心该有的样子——**平台无关**。

## 2.6 目录结构建议

抽象后，工程通常这样分层：

```
src/
├── core/                       ← 引擎核心，平台无关
│   ├── Application.cpp
│   └── Event.h
├── platform/                   ← 平台实现
│   ├── Window.cpp              ← 工厂实现（include 具体后端）
│   └── glfw/
│       ├── GLFWWindowImpl.h
│       └── GLFWWindowImpl.cpp
└── main.cpp
```

> 💡 对应到本仓库现在的扁平 `src/`，你可以先不分目录，把文件都放 `src/`，等模块多了再拆。
> CMake 的 `GLOB_RECURSE` 已经会递归收集子目录，分层不影响编译。

## 2.7 Pimpl 的选择（替代纯虚接口）

如果你觉得「搞一堆虚函数有运行时开销」，可以用 **Pimpl**（[基础篇 03 的 3.6 节](../basics/03-RAII与C++封装思想.md)）达到类似隔离：

```cpp
class Window {
public:
    Window(const Props& props);
    ~Window();   // 必须在 .cpp 定义（unique_ptr<Impl> 需完整类型）
    void swapBuffers();
    // ... 非 virtual，内部转调 m_impl
private:
    struct Impl;
    std::unique_ptr<Impl> m_impl;
};
```

| | 纯虚接口 | Pimpl |
|---|---|---|
| 运行时开销 | 一次虚函数调用 | 一次指针解引用 |
| 运行时换后端 | 支持（工厂返回不同子类） | 不支持（编译期固定） |
| 可读性 | 多一层继承 | 一个类 |
| 适合 | 引擎（可扩展、可插件） | 应用（性能敏感、后端固定） |

引擎通常选**纯虚接口**，因为可扩展性 > 那点虚函数开销。

---

## 2.8 小结

- 抽象出 `Window` 纯虚接口，引擎核心就不再认识具体窗口库——满足依赖倒置。
- `Window::create()` 工厂在平台层把「接口」和「实现」粘起来，核心只面向接口编程。
- 分层目录（core / platform）让依赖方向清晰：平台依赖 core，反之不行。
- 纯虚接口 vs Pimpl：引擎选纯虚（可扩展），应用选 Pimpl（零开销）。

## 🔧 练习

1. 把本仓库的 `GLFWManager` 改造成 `Window` 接口 + `GLFWWindowImpl`，保持 `main.cpp` 行为不变。
2. 加一个 `Window::getNativeWindow()` 虚函数（返回 `void*`），各后端返回自己的原生句柄——为 [05 篇 ImGui](05-集成ImGui.md) 做准备。
3. （进阶）实现一个 `HeadlessWindow`（无窗口、用于单元测试或服务器端渲染），它不依赖任何窗口库，`pollEvents/swapBuffers` 全空实现。体会接口抽象让你能「假造」一个窗口——这正是 [08 篇测试](08-测试与验证.md) 的基础。

## 📝 参考答案

### 1. `GLFWManager` → `Window` 接口 + `GLFWWindowImpl`

`Window.h`（core，照 2.2 节原样）+ `GLFWWindowImpl`（把 [基础篇 04](../basics/04-实现基础GLFWManager.md) 的类名改掉、继承 `Window`、override 所有纯虚函数、用 `setEventCallback` 替换那两个 setter）。工厂：

```cpp
// Window.cpp
std::unique_ptr<Window> Window::create(const Props& props) {
    auto w = std::make_unique<GLFWWindowImpl>();
    if (!w->init(props)) return nullptr;
    return w;
}
```

`main.cpp` 改为 `auto window = Window::create({...});`，行为不变。

### 2. `getNativeWindow()` 返回 `void*`

```cpp
// Window.h 接口
virtual void* getNativeWindow() const = 0;
// GLFWWindowImpl
void* getNativeWindow() const override { return (void*)m_window; }
```

为 [05 篇 ImGui](05-集成ImGui.md) 准备——`ImGui_ImplGlfw_InitForOpenGL((GLFWwindow*)window->getNativeWindow(), true)`。

### 3.（进阶）`HeadlessWindow`（Fake，测试用）

```cpp
class HeadlessWindow : public Window {
    bool m_shouldClose{false}; int m_w{800}, m_h{600}; EventCallback m_cb;
public:
    bool init(const Props& p) override { m_w=p.width; m_h=p.height; return true; }
    void shutdown() override {}
    void pollEvents() override {}
    void swapBuffers() override {}
    bool shouldClose() const override { return m_shouldClose; }
    void setShouldClose(bool v) override { m_shouldClose = v; }
    int  width()  const override { return m_w; }
    int  height() const override { return m_h; }
    void setVsync(bool) override {}
    void setEventCallback(EventCallback cb) override { m_cb = std::move(cb); }
    void* getNativeWindow() const override { return nullptr; }
    void simulateEvent(Event& e) { if (m_cb) m_cb(e); }   // 测试注入事件
};
```

这就是 [08 篇](08-测试与验证.md) 测试替身的基础——不依赖任何窗口库，能「假造」一个窗口。
